# PROMPT Generation Causal Audit

## 목적

이번 작업은 차트 프롬프트 문장을 바로 줄이기 위한 수정이 아니다.

PSOS의 PROMPT 경로가 왜 `핵심 판단 절차`보다 `모든 요구를 펼친 규칙집`을 만들기 쉬운지, 실제 생성 경로와 실제 결과에서 원인 표면과 증폭 단계를 구분하기 위한 진단이다.

## 실제 생성 토폴로지

처음에는 다음과 같은 직선 경로로 보았다.

```text
사용자 원문 → Goal Ledger → Compiler baseline → 실행기 입력 → 최종 프롬프트
```

하지만 코드상 Ledger와 baseline은 앞뒤 단계가 아니다. 둘 다 사용자 원문에서 따로 생성된 뒤 실행기에서 합류한다.

```text
사용자 원문 ─┬→ Goal Ledger ─────────────┐
              ├→ Prompt Compiler baseline ├→ PROMPT 실행기 입력 → 최종 프롬프트
              └───────────────────────────┘
실행기 공통 규칙 ─────────────────────────┘
```

따라서 `Ledger → baseline`의 길이 비율을 원인으로 해석하면 안 된다. 핵심 관찰 지점은 다음 둘이다.

1. 병렬 산출물이 실행기 입력에 어떤 방식으로 합류하는가
2. 최종 모델이 합류된 입력을 어떤 형태로 다시 전개하는가

## 실제 차트 프롬프트 사례

사용자가 실제로 받은 단타 차트 분석 프롬프트를 fixture로 고정해 측정했다.

| 표면 | 문자 수 | 의미 |
|---|---:|---|
| 사용자 원문 | 226 | 원래 목표와 조건 |
| Goal Ledger 렌더링 | 632 | 목표·제약·완료 조건의 재표현 |
| Prompt Compiler baseline | 431 | 원문과 일반 패턴 규칙 |
| PROMPT 실행기 전체 입력 | 2,389 | 원문·Ledger·baseline·공통 실행 규칙의 합류 |
| 최종 프롬프트 | 4,509 | 실제 생성된 규칙집 형태의 산출물 |

최종 프롬프트에는 다음 신호가 있었다.

- 제목 26개
- 규칙 계열 표현 29회
- 금지·확인 불가·단정 금지 계열 안전 문구 22회
- 동일한 사용자 원문이 실행기 입력 안에 정확히 2회 포함

기존 선형 trace에서는 `compiler_baseline → executor_input`이 5.543배로 가장 크게 보였다. 이 수치는 baseline이 단독으로 팽창했다는 뜻이 아니다. 실행기 입력이 baseline 외에도 Goal Ledger, 원문, 실행 규칙을 한꺼번에 포함하기 때문에 생긴 **합류 크기**다.

## 현재까지 지지되는 인과 구조

### 1. 원인 표면: 압축 없는 병렬 합류

PROMPT 실행기는 다음을 동시에 받는다.

1. Goal Ledger 전체
2. 사용자 요청 원문
3. 사용자 요청을 다시 포함한 Prompt Compiler baseline 전체
4. 경로 행동과 공통 실행 규칙

같은 사용자 요구가 원문, Ledger 문장, baseline 내부 원문으로 재노출된다. 어느 표현을 대표본으로 삼고 어느 표현을 흡수할지 정하는 계약은 없다.

이 때문에 모델은 반복을 중복으로 버리기보다 `반드시 보존해야 하는 서로 다른 조건`으로 해석하기 쉽다.

### 2. 보존 압력: 모두 명시하는 쪽이 안전하다

PROMPT 실행기는 baseline의 목적·제약·출력 계약을 보존해야 한다. Goal Ledger 역시 목표와 고정 조건을 바꾸지 말라고 요구한다.

반면 다음 작업은 명시되어 있지 않다.

- 같은 의미의 요구를 하나의 원리로 통합
- 핵심 판단·보조 재료·안전 규칙·출력 취향의 위계 설정
- 대표 표현을 고른 뒤 나머지 중복 제거
- 세부 규칙을 핵심 알고리즘에 흡수해도 보존으로 인정

따라서 누락 위험이 있는 압축보다, 모든 표현을 독립 규칙으로 다시 쓰는 방식이 시스템 지시를 안전하게 충족한다.

### 3. 보조 압력: Compiler 패턴은 완전성을 보상한다

`prompt_runtime.py`의 baseline은 사용자 요청을 그대로 포함한다. `pattern-only`는 그 뒤에 누락 점검과 정확한 출력 형식 규칙을 덧붙인다.

```text
원문을 포함한 baseline
+ 수행 및 출력 규칙
+ 선택된 경우 작업별 추가 규칙
```

이 구조에는 중복 통합이나 규칙 증가 비용을 평가하는 반대 기준이 없다. 다만 실제 사례에서 baseline은 431자로, 전체 실행기 입력 2,389자보다 훨씬 작았다. 따라서 **baseline 단독을 주원인으로 확정할 근거는 없다.** 현재는 합류 뒤 완전성 압력을 높이는 보조 요인으로 본다.

### 4. 증폭 단계: 최종 모델이 합류물을 문서 구조로 펼친다

실행기 입력 2,389자는 최종 프롬프트에서 4,509자로 늘었다. 단순 길이 증가보다 중요한 것은 형태 변화다.

- 요구 하나가 독립된 제목과 규칙으로 분리됨
- 안전 규칙이 여러 위치에서 반복됨
- 출력 형식이 8개 섹션으로 확장됨
- 핵심 판단 알고리즘과 보조 설명의 위계가 약해짐

즉 실행기 입력의 중복 합류가 **원인 표면**이고, 최종 PROMPT 모델은 이를 규칙·섹션 형태로 전개하는 **증폭기**로 작동했다.

### 5. Goal Ledger 평면 구조는 아직 2차 가설이다

`fixed_constraints`는 핵심 판단 기준, 보조 재료, 안전 규칙, 출력 선호를 구분하지 않는 문자열 배열이다. 이것이 독립 규칙 전개를 돕는 것은 합리적인 가설이다.

하지만 한 사례만으로 다음을 확정하지 않는다.

- Ledger 필드 분리가 반드시 필요함
- Ledger가 가장 큰 원인임
- 기존 스키마를 즉시 바꾸는 것이 최선임

원문·baseline 중복을 먼저 제거했을 때도 같은 과잉이 남는지 비교해야 한다.

## 결과 포장은 별도 문제다

`result.md`가 최종 프롬프트, 목표·경로 설명, limitations, 브리지 검증 한계를 한 문서에 붙인 것은 생성 인과와 다른 문제다.

```text
생성 품질 문제
→ 왜 규칙집 형태의 프롬프트가 나왔는가

결과 포장 문제
→ 왜 복사용 프롬프트와 시스템 기록이 한 덩어리로 보였는가
```

두 문제는 별도 수정해야 한다.

## 추가된 진단 파일

PROMPT가 포함된 품질 실행은 다음을 남긴다.

```text
prompt_generation_trace.json
prompt_generation_trace.md
prompt_generation_causal_audit.json
prompt_generation_causal_audit.md
prompt_ablation/manifest.json
```

`trace`는 단계별 텍스트 크기·반복·형식 신호를 기록한다. `causal_audit`은 병렬 분기와 실행기 합류를 따로 모델링한다. `prompt_ablation`은 원본을 덮어쓰지 않고 네 가지 통제 입력을 만든다.

진단은 기존 `result_markdown`을 수정하지 않으며, 차트·상품·댓글 같은 도메인별 정답을 코어에 넣지 않는다.

## 현재 결론

현재 사례가 가장 강하게 지지하는 설명은 다음과 같다.

```text
원문에서 Ledger와 baseline이 병렬 생성됨
→ 원문까지 포함해 세 표면이 압축 없이 실행기에 합류
→ 보존·완전성 지시 때문에 중복을 버리기 어려움
→ 최종 모델이 각 표현을 별도 규칙과 출력 섹션으로 전개
→ 핵심 판단 절차보다 규칙집이 커짐
```

따라서 지금 바로 `프롬프트를 30% 줄여라` 같은 출력 제한을 넣는 것은 원인 수정이 아니다.

## 통제 비교

입력 합류를 다음 네 방식으로 바꾼다.

1. 현재 방식: Ledger + 원문 + 원문 포함 baseline
2. 원문 중복 제거: Ledger + baseline
3. Ledger 최소화: 목표·고정 조건·완료 조건 + baseline
4. 대표 brief 사용: 핵심 목표·고정 조건·출력 계약을 한 번만 정규화

품질 run이 끝나면 네 입력 파일은 자동으로 생성된다. 실제 동일 모델 비교는 비용이 드는 명시적 명령으로만 실행한다.

```powershell
python -B .\scripts\problem_solving_prompt_ablation_run.py `
  --run-dir .\runs\RUN_ID
```

실행기는 원래 PROMPT executor의 실제 모델·reasoning·sandbox 설정을 `route.json`에서 복원한다. 현재 결과는 다시 생성하지 않고 기준값으로 사용하며, 나머지 세 변형과 후보명을 가린 블라인드 평가를 실행한다. 결과는 다음에 저장한다.

```text
prompt_ablation/results/*.md
prompt_ablation/results/*.json
prompt_ablation/comparison.json
prompt_ablation/comparison.md
```

비교 기준은 다음과 같다.

- 요구 누락 여부
- 핵심 작업 절차의 선명도
- 제목·규칙·안전 문구와 의미 반복
- 출력 형식이 작업을 압도하는지
- 실제 재사용 가능성

짧다는 이유만으로 승자를 고르지 않는다. 토큰 겹침은 표면 신호로만 기록하고, 별도 블라인드 평가가 조건 보존과 절차 우선성을 판정한다.

현재 비교는 **생성된 프롬프트 자체**까지다. 각 프롬프트를 실제 차트 이미지에 적용한 매매 판단 품질은 승자 후보를 좁힌 뒤 별도 적용 실험으로 확인한다.

원문 중복 제거만으로 개선되면 실행기 합류가 주원인이다. 그래도 규칙집 성향이 강하면 Ledger 위계와 Compiler 패턴을 다음 변수로 분리한다.
