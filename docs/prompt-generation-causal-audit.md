# PROMPT Generation Causal Audit

## 목적

이번 작업은 차트 프롬프트 문장을 바로 줄이기 위한 수정이 아니다.

PSOS의 PROMPT 경로가 왜 `핵심 판단 절차`보다 `모든 요구를 펼친 규칙집`을 만들기 쉬운지, 실제 생성 경로에서 처음 과잉이 생기는 지점을 찾기 위한 진단 단계다.

## 현재 생성 경로

```text
사용자 요청
→ Goal Ledger
→ Prompt Compiler baseline
→ PROMPT 실행기 입력
→ 최종 프롬프트
→ result.md 포장
```

각 단계는 서로 다른 역할을 하지만, 현재는 이전 단계의 내용을 요약·대체하지 않고 다음 단계에 누적하는 경향이 있다.

## 코드에서 확인된 구조

### 1. Prompt Compiler baseline은 additive 방식이다

`prompt_runtime.py`의 baseline은 사용자 요청을 그대로 넣는다. `pattern-only`는 baseline 뒤에 `[수행 및 출력 규칙]`을 붙이고, `active`는 다시 `[작업별 추가 규칙]`을 붙인다.

```text
baseline
+ pattern instructions
+ active source rules
```

이 경로에는 다음 작업이 없다.

- 같은 뜻의 요구 통합
- 핵심 판단과 보조 규칙의 위계 설정
- 새 규칙을 넣을 때 기존 중복 제거
- 규칙 증가가 실제 결과를 개선하는지 비교

따라서 선택된 패턴이 많을수록 안전하게 빠짐없이 쓰는 방향으로는 강화되지만, 간결한 판단 알고리즘으로 압축되지는 않는다.

### 2. PROMPT 실행기는 같은 요구를 세 표면에서 다시 받는다

PROMPT executor 입력에는 다음이 동시에 들어간다.

1. Goal Ledger 전체
2. 사용자 요청 원문
3. 사용자 요청을 다시 포함한 Prompt Compiler baseline 전체

즉 하나의 요구가 원문, Ledger 문장, baseline 규칙으로 변형돼 반복 노출된다. Executor에는 어느 표현을 대표본으로 삼고 어느 표현을 흡수해야 하는지 계약이 없다.

### 3. Goal Ledger는 보존에는 강하지만 위계 표현이 없다

현재 `fixed_constraints`는 평면 문자열 배열이다. 다음 역할이 구조적으로 구분되지 않는다.

- 결과를 결정하는 핵심 판단 기준
- 판단에 사용하는 보조 재료
- 거짓 확신을 막는 안전 규칙
- 단순한 출력 선호

그래서 Executor는 서로 다른 역할의 조건을 같은 무게의 독립 규칙으로 전개하기 쉽다.

### 4. PROMPT 검증은 완전성을 보기 쉽고 작동 품질을 보기 어렵다

Result Contract는 PROMPT 결과에 실제 최종 프롬프트가 있는지, 재사용 인터페이스와 요청된 요소가 들어갔는지를 확인할 수 있다.

하지만 현재는 다음을 직접 검증하지 않는다.

- 실제 입력에 실행했을 때 핵심 결론이 빨리 나오는가
- 여러 규칙 때문에 판단이 분산되는가
- 출력 형식 때문에 빈 항목을 억지로 채우는가
- 같은 안전 규칙이 여러 위치에 반복되는가
- 더 짧은 baseline보다 실제 결과가 나아졌는가

따라서 긴 체크리스트도 요구 누락이 적으면 성공 결과로 통과할 수 있다.

### 5. 시스템 포장은 별도의 혼란을 추가한다

`result.md`는 최종 산출물에 목표·경로·한계를 함께 붙인다. 수동 브리지는 자신의 receipt 한계도 execution limitations에 추가한다.

이 문제는 프롬프트가 규칙집이 된 원인은 아니지만, 다음 세 가지가 한 결과처럼 보이게 한다.

- 실제 복사할 프롬프트
- 프롬프트 자체의 현실적 한계
- 브리지와 검증 시스템의 한계

따라서 생성 품질 문제와 결과 포장 문제는 따로 수정해야 한다.

## 이번에 추가한 진단 기록

PROMPT가 포함된 품질 실행은 다음 파일을 남긴다.

```text
prompt_generation_trace.json
prompt_generation_trace.md
```

진단은 실제 run artifact만 사용해 다음을 기록한다.

- 사용자 원문, Goal Ledger, baseline, Executor 입력, 최종 프롬프트의 크기
- 각 구간의 길이 증가와 새 토큰 비율
- 최종 프롬프트의 유사 규칙 쌍
- 최종 문장과 원문·Ledger·baseline의 어휘 연결
- 평면 Ledger, additive baseline, 삼중 입력, 형식 압력, 안전 규칙 우세 신호

진단은 프롬프트 내용을 바꾸지 않으며, 차트·상품·댓글 같은 도메인 규칙을 코어에 넣지 않는다.

## 아직 확정하지 않은 것

코드 구조만으로 다음을 단정하지 않는다.

- 어느 단계가 모든 PROMPT 과잉의 유일한 원인인지
- Goal Ledger 필드를 바로 늘리는 것이 정답인지
- baseline 패턴을 삭제해야 하는지
- 출력 섹션 수에 고정 상한을 둬야 하는지
- 프롬프트마다 실제 실행 시험이 항상 필요한지

이 판단은 여러 실제 PROMPT run의 trace를 비교한 뒤 한다.

## 다음 비교 실험

최소 세 종류의 PROMPT 요청을 같은 방식으로 실행한다.

1. 판단 알고리즘이 중요한 분석 프롬프트
2. 자연스러운 문체와 의도 보존이 중요한 작성 프롬프트
3. 자료 조사 절차와 근거 관리가 중요한 리서치 프롬프트

각 run에서 다음 질문에 답한다.

- 첫 번째 큰 팽창은 어느 구간에서 생겼는가
- baseline의 패턴 규칙이 최종 프롬프트에서 실제로 반복됐는가
- Ledger의 조건 중 어떤 것이 핵심 절차가 아니라 독립 섹션이 됐는가
- 최종 형식이 실제 판단보다 더 많은 공간을 차지하는가
- 서로 다른 도메인에서도 같은 원인이 반복되는가

공통 원인이 확인된 뒤에만 Prompt Compiler 또는 Ledger 계약을 바꾼다. 차트 프롬프트 하나만 짧게 만드는 수정은 이 단계의 목표가 아니다.
