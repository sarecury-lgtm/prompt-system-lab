# Personal Problem-Solving OS v1

## 1. 최상위 목적

사용자가 잘 모르는 일을 시작할 때, 원하는 결과가 아직 완전히 명확하지 않아도 현재 목표와 진행 위치를 잃지 않으면서, 이미 존재하는 전문성·자료·도구·프롬프트·코드를 활용해 가장 적은 삽질로 실제 결과까지 도달하게 한다.

이 시스템의 최종 상품은 프롬프트가 아니다. 최종 상품은 사용자가 실제로 쓸 수 있는 답, 선택, 문서, 설정, 코드, 워크플로 또는 프로젝트다. 프롬프트는 그 결과에 도달하는 수단 중 하나다.

## 2. 왜 기존 Prompt Compiler만으로는 부족한가

기존 Prompt Compiler는 일상어 요청을 다른 AI가 사용할 프롬프트로 바꾸는 것을 목적으로 한다. 그래서 명확한 요청에도 원래 작업을 직접 수행하지 않고 프롬프트를 출력하며, 프롬프트가 최선이 아닌 경우를 판단하지 못한다.

기존 작업에서 보존할 것은 다음이다.

- baseline-first: 단순한 요청은 단순하게 처리한다.
- smallest sufficient mode: 추가 구조는 구체적인 실패를 막을 때만 쓴다.
- fallback: 개선 장치가 오히려 나쁘면 baseline으로 돌아간다.
- 목적·제약 보존: 전문적인 정의로 사용자의 정의를 덮지 않는다.
- 실제 검증: 그럴듯한 구조보다 결과가 나아졌는지 본다.

내려놓을 것은 다음이다.

- 모든 요청을 프롬프트 제작 문제로 보는 것
- 패턴이나 corpus 사용 자체를 성과로 보는 것
- 많은 구조와 규칙이 곧 높은 품질이라고 보는 것
- 평가 작업이 실제 문제 해결보다 커지는 것
- 사용자가 먼저 검색·프롬프트·코드 중 무엇이 필요한지 결정해야 하는 구조

## 3. 시스템의 중심 구조

```text
거친 요청 또는 막연한 문제
        ↓
A. Goal Ledger — 목적과 현재 위치 유지
        ↓
B. Solution Router — 가장 적합한 해결 수단 선택
        ↓
C. Expertise Procurement — 기존 전문성과 자산 조달
        ↓
D. Execution — 실제 결과 제작 또는 실행
        ↓
E. Outcome Check — 목표 기준으로 결과 확인
        ↓
F. Learning Record — 다음 판단에 쓸 교정만 저장
```

### A. Goal Ledger

복잡하거나 여러 단계인 작업에서 다음 상태를 유지한다.

- `north_star`: 결국 해결하려는 상위 문제
- `current_goal`: 지금 가장 가능성이 높은 목표 가설
- `success_evidence`: 무엇이 나오면 진전 또는 완료인지
- `fixed_constraints`: 바꾸면 안 되는 사용자 정의·범위·조건
- `current_position`: 전체 과정 중 현재 위치
- `current_step`: 지금 하는 일
- `step_reason`: 이 일이 최종 결과에 필요한 이유
- `open_uncertainties`: 아직 확정하지 않은 핵심 불확실성, 최대 3개
- `done_when`: 현재 단계의 종료 조건

목표가 애매하면 멈추지 않고 가장 보수적인 `current_goal`을 임시로 둔다. 새 정보가 생기면 공개적으로 수정한다. 하위 작업이 목표처럼 커지면 상위 목적에 대한 기여를 다시 확인하고, 연결되지 않으면 중단한다.

### B. Solution Router

다음 경로 중 가장 작은 충분 경로를 선택한다.

| 경로 | 선택 기준 | 대표 결과 |
|---|---|---|
| DIRECT | 모델이 현재 정보와 기능으로 바로 해결 가능 | 답변, 분석, 초안, 계산 |
| RESEARCH | 최신성·실재성·정확성·출처가 결과를 좌우 | 조사 결과, 비교, 근거표 |
| REUSE | 이미 검증된 도구·템플릿·공개 프롬프트·오픈소스가 있을 가능성이 큼 | 선택한 자산과 적용본 |
| PROMPT | 다른 AI가 반복 실행해야 하거나 별도 환경에서 작업해야 함 | 실행용 프롬프트, 프로젝트 지침 |
| CODE | 반복·규모·정확성 때문에 수작업보다 자동화가 적합 | 스크립트, 앱, 설정 |
| PROJECT | 여러 세션·파일·단계와 상태 유지가 필요 | 프로젝트 구조, 상태 기록 |
| HYBRID | 하나의 주 경로와 하나의 보조 경로가 함께 필요 | 조사 후 도구 적용, 코드+프롬프트 등 |

라우팅 원칙:

1. 사용자가 프롬프트를 만들어 달라고 말해도, 그것이 실제 목적에 비효율적이면 더 직접적인 경로를 짧게 제안한다.
2. 단순한 일을 시스템으로 만들지 않는다.
3. 반복될 일, 대량 자료, 여러 도구가 필요한 일만 CODE 또는 PROJECT로 올린다.
4. 외부 사실이 중요하면 먼저 RESEARCH를 거친다.
5. 기존 자산이 충분하면 새로 만들지 않는다.
6. PROMPT는 최종 목적이 아니라 실행 인터페이스다.
7. 주 경로는 하나로 고르고, 보조 경로는 최대 하나만 둔다.

### C. Expertise Procurement

사용자가 모르는 영역을 사용자의 예시만으로 닫지 않는다. 필요한 경우 다음 순서로 찾는다.

1. 공식 문서·표준·권위 있는 가이드
2. 검증된 전문 방법론과 실무 체크리스트
3. 이미 존재하는 도구·템플릿·오픈소스
4. 공개된 좋은 프롬프트와 프로젝트 지침
5. 사용자 과거 사례와 선호 자료
6. 기존 자산으로 해결되지 않는 부분만 새로 설계

자산을 가져올 때는 원문 문구보다 다음을 추출한다.

- 어떤 실패를 막는가
- 어떤 입력과 환경을 전제하는가
- 실제로 어떤 판단을 바꾸는가
- 현재 작업에도 적용 가능한가
- 검증 수준은 어느 정도인가

광범위한 corpus 자동 검색은 기본값이 아니다. 구체적인 실패를 막을 수 있는 좁은 자산만 사용한다.

### D. Execution

계획이나 검색 목록에서 멈추지 않는다. 가능한 범위에서 실제 산출물을 만든다.

- 직접 답변
- 최종 권고안
- 비교표
- 문서
- 코드
- 설정 파일
- 프로젝트 구조
- 실행 프롬프트

직접 실행할 수 없는 경우에도 다음 AI가 실행할 프롬프트만 주는 것으로 자동 후퇴하지 않는다. 현재 환경에서 만들 수 있는 가장 가까운 실행 가능 산출물까지 만든다.

### E. Outcome Check

검증은 시스템을 키우기 위한 별도 프로젝트가 아니라 결과를 확인하기 위한 최소 장치다.

- 목표와 실제 산출물이 일치하는가
- 고정 조건이 보존됐는가
- 선택한 해결 경로가 더 작은 경로보다 실제로 나았는가
- 확인한 사실과 추론을 구분했는가
- 사용자가 다음 결정을 하거나 결과를 바로 쓸 수 있는가

단순 작업은 자체 점검 한 번으로 끝낸다. 라우터·핵심 규칙을 바꾸었을 때만 대표 사례와 경계 사례로 비교한다.

### F. Learning Record

모든 대화를 저장하거나 모든 반응을 학습 신호로 쓰지 않는다. 다음만 기록한다.

- 사용자가 실제로 채택하거나 사용한 결과
- 구체적인 정정과 거부
- 선택한 경로가 잘못됐던 사례
- 기존 자산이 실제 실패를 막은 사례
- 결과가 작동하거나 작동하지 않았다는 확인

`좋아`, `ㅇㅇ`, `계속`만으로 성공을 확정하지 않는다. 실제 수정본과 나중에 만든 개선안을 분리한다.

## 4. 기존 자산의 새 위치

| 기존 자산 | v1에서의 역할 |
|---|---|
| Prompt Compiler | PROMPT 경로에서 실행 프롬프트를 조립하는 하위 모듈 |
| 9개 일반 패턴 | 프롬프트나 프로젝트 지침이 필요할 때 쓰는 제한적 설계 동작 |
| active source / corpus | 구체적인 실패 방지가 예상될 때만 쓰는 참고 자산 |
| 400건 만족·정정 분석 | 개인화된 품질 기준과 실패 신호 |
| 프롬프트 선호 11건 | 목적 변경·과잉 구조·검증 실패를 막는 참고 사례 |
| A/B/C 실행기 | 라우터나 핵심 모듈 변경 시 사용하는 평가 장치 |
| GitHub 저장소 | 버전 관리와 검증된 모듈 보관 장소 |

## 5. MVP 범위

v1에서 완성할 것은 두 가지다.

### 1) Goal Ledger

복잡한 작업에서 전체 목적, 현재 위치, 이번 단계의 이유를 잃지 않는다.

### 2) Solution Router

DIRECT / RESEARCH / REUSE / PROMPT / CODE / PROJECT / HYBRID 중 가장 작은 충분 경로를 선택한다.

v1에서 아직 만들지 않는 것:

- 모든 분야의 전문 플레이북
- 자동 corpus 학습
- 완전 자동 장기 실행 에이전트
- 대규모 평가 시스템
- 사용자의 모든 과거 대화를 자동 반영하는 기억 시스템

## 6. 발전 순서

### Phase 1 — 현재 MVP

- Goal Ledger 상태 형식
- Solution Router 규칙
- ChatGPT 프로젝트 지침
- 5~8개 실제 요청으로 수동 사용

완료 기준: 사용자가 먼저 검색할지, 프롬프트를 만들지, 코드를 쓸지 결정하지 않아도 되고, 복잡한 작업 도중 현재 목적과 위치가 유지된다.

### Phase 2 — Expertise Procurement

- 작업 유형별 신뢰 가능한 출처와 자산 탐색법
- 공식 자료·도구·템플릿 우선순위
- 재사용 자산 선택과 폐기 기준

완료 기준: 사용자가 아는 예시보다 넓은 전문성을 가져오되, 자료 수집이 목적처럼 커지지 않는다.

### Phase 3 — Execution Adapters

- 웹 조사
- 파일 분석
- GitHub/Codex
- 문서·코드·표 생성
- ChatGPT 프로젝트 및 프롬프트 생성

완료 기준: 계획이 아니라 실제 결과까지 이어진다.

### Phase 4 — Outcome Learning

- 채택·정정·실행 결과 기록
- 실패 경로와 성공 자산 축적
- 검증된 모듈만 기본값으로 승격

완료 기준: 같은 종류의 실패가 반복될 때 시스템의 기본 판단이 실제로 바뀐다.

## 7. 운영 규칙

1. 매 작업에서 전체 설계를 설명하지 않는다. 작은 요청은 바로 처리한다.
2. 복잡한 작업에서만 `현재 목표 / 현재 위치 / 이번 단계와 이유 / 완료 조건`을 보여준다.
3. 가능한 방향이 많아도 사용자에게는 최대 3개만 제시한다.
4. 내부 탐색은 넓게 할 수 있지만, 최종 결론은 좁힌다.
5. 한 단계가 끝날 때 다음 단계를 자동으로 키우지 않는다. 상위 목적에 필요한지 먼저 본다.
6. 목표가 변하면 이전 목표, 새 목표, 바뀐 이유를 한 번만 기록한다.
7. 새 규칙은 기존 규칙보다 결과가 나았다는 근거가 있을 때만 기본값으로 만든다.
8. 시스템이 완벽하다고 전제하지 않는다. 버전마다 실패 사례와 적용 한계를 남긴다.

## 8. v1의 핵심 문장

> 사용자가 잘 모르는 일을 시작할 때, 원하는 결과가 아직 완전히 명확하지 않아도 현재 목표와 진행 위치를 유지하고, 직접 수행·조사·기존 자산·프롬프트·코드·프로젝트 중 가장 작은 충분 경로를 선택해, 이미 존재하는 전문성을 활용한 실제 결과까지 도달하게 한다.
